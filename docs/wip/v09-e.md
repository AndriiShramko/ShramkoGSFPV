## The question

The owner flies a Radiomaster GX12 over Bluetooth (the ExpressLRS module's "BLE Joystick" mode, which the
PC sees as a plain gamepad: "8 axis 0 button gamepad") and reports about 300 ms between moving a stick and
the green stick on the screen moving; the drone is late too. He set no expo and no rates. v0.8 changed how
we sample a gamepad (stamping with `Gamepad.timestamp`). Questions: (1) does OUR code add delay on a
Bluetooth-like timeline; (2) if yes, fix it; (3) show the pilot the measured report interval so the rest
is visible and honest; (4) say what Bluetooth itself costs and what he can do.

## The path of one stick move (what we control, what we do not)

```
stick -> radio -> [ELRS module: BLE notify per CRSF frame] -> BLE link (connection interval) ->
Windows BLE HID driver -> Chrome raw-input window (WM_INPUT, stamps Gamepad.timestamp) ->
Chrome gamepad provider publishes every 4 ms -> getGamepads() in the page        <- we start here
-> GamepadSource.poll (MessageChannel loop, >= 2 ms apart) -> Controls.raw -> session.input -> SimClock queue
-> the next animation frame steps the physics (applied at its stamp) and draws -> compositor -> display
```

Everything left of the arrow is the device, the link and Chrome (sources in the research part below).
Everything right of it is ours: the poll loop, the stamp, the queue, the frame that draws the stick.

## Where our code could add delay (hypotheses, each tested by the harness)

- H1 `fresh` is decided by `Gamepad.timestamp !== lastTs` only. A browser or device that changes values
  without moving the timestamp (frozen) is only noticed at the 20 ms keep-alive: up to 20 ms late, and
  stamped at the poll. Same in v0.7 and v0.8 (the control cannot tell them apart); not a v0.8 regression.
- H2 v0.8 stamps with `Gamepad.timestamp`. Cannot add delay (earlier stamp = earlier application), but
  stale (> 100 ms old), future or backwards timestamps must fall back / clamp correctly. Tested.
- H3 Bursty links (several reports together every 50-100 ms): the page sees the last of a burst; check the
  burst does not stall or reorder and the stamp is the burst's arrival.
- H4 Polling bound to the animation frame would add up to one display period (33 ms at the owner's 30 Hz);
  ours is a MessageChannel loop, not rAF-bound. Shown as the control.
- H5 The on-screen stick is drawn at the next animation frame; at 30 Hz that is up to 33 ms and cannot be
  lower in a browser. Reported, not "fixed".

## Design

1. `packages/input/src/link.ts` — `LinkMeter`: a pure meter of the intervals between a device's new
   samples (median, p95, jitter, longest gap, bunching, rate) over a sliding window, with one verdict
   (`ok` / `slow` / `bursty`) and the numbers the note quotes. No DOM, tested on synthetic timelines.
2. `GamepadSource` and `HidSource` feed it; `GamepadSource` also treats a value change with a frozen
   timestamp as a new sample (H1 fix).
3. A deterministic harness (`tools/bench/test/pad-timeline.test.ts` + `tools/bench/test/helpers/pad-sim.ts`)
   drives the REAL `GamepadSource` on a virtual clock and a virtual event loop with the synthetic timelines,
   against the v0.7 file (`git show 097300d:apps/fly/src/devices/gamepad.ts`, kept as a fixture) as control.
4. The radio check screen and F3 show the measured interval, rate and jitter; above ~10 ms or bursty a
   short note says a USB cable is faster (4 languages).
