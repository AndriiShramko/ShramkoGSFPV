## Design

### 1. A 3-position switch made of two button bits is one switch input (`packages/input`)

`SwitchInput` gets a third kind, `{ kind: 'bits', lo, hi }`: two mutually exclusive button bits of one
switch. `lo` on = low position, `hi` on = high, neither = middle (both on, which the device never sends,
reads as the middle). The previous lane skipped it for three reasons, each solved here:

- **Saved profiles.** Profiles stay version 1; `validSwitchInput` reads the new kind (bits 0..23, lo != hi).
  An older build drops a range or mode switch it cannot read and keeps the profile (its existing rule),
  so nothing breaks backwards; tests load profiles saved before this lane unchanged.
- **Betaflight channel numbers.** A device gets an optional channel table, `Profile.channels`: its radio
  channels in order, CH1 first, each a `SwitchInput` (a pair is ONE channel). `channelOf` / `channelInput`
  / `inputName` use the table when the profile has one, else the EdgeTX USB joystick numbering as before
  (axes CH1..CH8, buttons CH9..CH32). A Betaflight `diff` import then puts AUX1 (CH5) of a DJI pilot's
  quad on the DJI's flight-mode switch, the same channel it is on the real quad (O4 air unit, SBUS).
- **Screens that name channels.** One naming function (`inputName`): a pair with a table is its channel
  ("CH5"); without one "CH13/14" on a USB radio, "buttons 5/6" on a gamepad (new i18n keys).

Where the pair is found: the wizard's mode-switch watch (`ModeSwitchDetector`) and the Switches screen's
"flip to assign" report a pair when one bit goes off and another comes on within a flip (end to end,
with or without the short middle seen in the recording), and a recognised device names its pairs up
front (`pairs`), so a flip through the middle position is the same switch.

### 2. Known controllers (data, not if-branches)

`packages/input/src/known-devices.ts`: a table of known controllers. Each entry: how it is matched (USB
vendor/product id + the descriptor's shape for WebHID; the Gamepad API id string's vendor/product and its
axis/button counts), the sticks by HID usage (Mode 2), the arm control, the flight-mode switch and its
positions -> Angle / Horizon / Acro, the Betaflight channel table, every control's label, and for every
fact where it comes from: `measured` (evidence path), `sourced` (URL) or `assumed` (the reason).
`recogniseHid(device)` / `recogniseGamepad(pad)` turn a match into a ready profile (axes resolved from
the descriptor's usages, or the Gamepad API's usage order), so the app has no device names in code.

- **DJI Virtual Joystick** (USB 2ca3:1021, gamepad, 5 x int16 -660..660, 24 buttons: the DJI FPV Remote
  Controller 3; DJI uses the same ids for other controllers, so the descriptor's shape must match too).
- **EdgeTX / OpenTX USB joystick**: recognised (name), no default mapping: the channel order and the
  switches are the pilot's model setup in the radio (AETR / TAER, arm on any channel), so the wizard
  stays. ELRS is a radio link, not a USB device: an ELRS radio runs EdgeTX and is this entry.

A known controller connects and goes straight to the check screen with its profile (the wizard is not
run): live bars labelled with each control, the arm, the mode switch row, every button and switch lit
as it is pressed, the provenance of the layout; Fly saves it (next time it flies at once, as any
checked setup), Reverse / Set again / Recalibrate still override. Unknown controllers keep the wizard.

### 3. Latency (item 7)

Gamepad API vs WebHID inside the page: the gamepad is polled at up to 500 Hz by a MessageChannel loop
(not once per display frame), but a sample is stamped with the poll time, and the physics applies an
input at its stamp; a WebHID report is stamped by the browser when it is dispatched. Measure with fake
devices on the local release (the owner's 30 Hz display, a real scan drawing): the stamp error and the
delivery delay per path; fix: stamp a gamepad sample with `Gamepad.timestamp` (the browser's own
sampling time, the page clock) when it is fresh and plausible. Numbers before / after.

### 4. Sensitivity (item 7)

How stick values reach the physics: HID logical range -> -1..1 (DJI raw / 660, EdgeTX (v - 1024) / 1024),
then the profile's centre and ends from the wizard (the extremes seen while setting up), deadband,
then the rates (expo lives in the rates). Check whether a short stir gives a narrow range (the stick
saturates early = more sensitive) with the DJI recording and the simulated people, against an EdgeTX
radio; a known controller uses its full logical range (measured for the DJI: every stick reaches
+-660) and a deadband that is continuous (no step at its edge). Numbers before / after.

## Results (for the lead)

What the owner gets (items 4/5 and 7):

- **DJI out of the box.** The DJI FPV Remote Controller 3 (USB 2ca3:1021, "DJI Virtual Joystick") is
  recognised on WebHID and on the Gamepad API. On the device choice a stick moved is enough: the
  Controls screen opens its check screen by itself (no wizard): sticks Mode 2 at full range, the flight
  mode switch N / S / M = Angle / Horizon / Acro as ONE 3-position switch, start/stop toggles the arm
  (throttle down), its Betaflight channels (CH5 mode switch, CH6 C2...). Below the stick rows: every
  control of the controller, live, labelled, with where its layout comes from. Fly saves it; next
  time it flies at once. A setup the wizard saved for it before offers "Use the known setup".
  Picking "Radio or controller over USB" stops that pad watch (a pad the browser shows while its
  device chooser is open does not take over); a chooser closed with no device starts it again
  (hid-source-probe dji-pad-chooser / dji-pad-cancel; controls: the pad opens at 0.55 s with no pick,
  a build that does not stop the watch hands the chooser's pick to the pad at 0.85 s).
- **3-position switches from two bits** are one switch everywhere: wizard mode row, Switches screen
  (flip to assign takes the pair), HUD names, Betaflight import (a DJI-flown quad's AUX1 lands on the
  DJI's mode switch).
- **Delay.** The Gamepad API path is not polled once per frame (500 Hz loop): a change reaches the page
  in 0.9 ms (median) against WebHID's 3.6 ms at the owner's 30 Hz; under load the gamepad move was
  applied up to 25 ms late in physics time (stamped at the poll): now at the browser's sample time
  (0 ms). The visible delay is bound by the 30 Hz display (17-25 ms to the first frame that can show
  it, plus the display's own). The controller's own delay needs the real controller.
- **Sensitivity.** The owner's real stir reached +-660 on every stick, so the DJI was not made more
  sensitive by calibration (it reads its full scale as an EdgeTX radio does). The wizard in general
  gave short strokes to people who do not push to the very end: fixed (END_SNAP), 72 -> 13 of 432
  simulated radio pilots with a stick >10 % too sensitive. The DJI's spring-centred throttle (= 50 %),
  its shorter sticks and expo / rates set in his previous radio's EdgeTX model are the likely rest:
  the check screen says how to stop the throttle spring (DJI's F1 / F2 screws).

Assumed (the check screen marks them "not confirmed yet"; the 30-second check in
`docs/research/radios/dji-rc3.md` confirms them): stick directions (up / right positive), which bit
pair is the flight-mode switch (6/7) and its N end (bit 6), the order of the four buttons (start/stop
= bit 2 arms). Measured: axes X/Rx horizontal and Y/Z vertical, pairs X+Y and Z+Rx, two 3-position
switches on bits 4/5 and 6/7, the throttle springs, rest offsets. Sourced: the controls (DJI's
manual), axis 1-4 = roll, pitch, throttle, yaw (Uncrashed, DJI FPV RC 2), the Betaflight AUX order
(Oscar Liang, RC 3 + O4).
