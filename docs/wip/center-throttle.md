## 2. Design

- **Preference** `input.throttleStyle`: enum `auto | centred | zero`, default `auto`, scope global, `persist: false`, `apply: 'live'`, `action: 'throttle.style'`, shown `settings, key, controls`. The store holds the style of the controller in use; the truth is per controller in its `Profile`: new optional `throttleStyle?: 'centred' | 'zero'` (pilot's choice; absent = auto) and `throttleRest?: 'centre' | 'bottom' | 'parked'` (measured). A new builtin `app/builtin/throttle-style.ts` copies the profile's choice into the store on every input change and writes a store change back into the profile (`saveProfile`). Profile stays version 1; `checkProfile` drops unknown values of both fields. Touch and keyboard: the setting does nothing (easy play already flies them); the row says so.
- **Detection (auto).** Resolved style = pilot's choice, else the rest seen on this connection, else `Profile.throttleRest` (wizard / known check), else the known table's `throttleSprings` (DJI -> centred), else `zero`. Rest rule on mapped `ch[2]` (-1..1, half range = 1): still = within `STILL_TOL` 0.04 for `STILL_MS` 500 (reused from `calib.ts` TUNING); `|ch2| <= CENTRE_TOL` 0.15 -> centre; `ch2 <= -(1 - END_TOL)` = -0.9 -> bottom; else parked (parked counts as zero). The DJI's measured offsets (1.7 %, 1.2 %) are inside 0.15. Connection rest is taken once, from the first still window while disarmed; it never changes the style in flight. Wizard: the throttle channel's `rest` from step 'centre' is saved as `throttleRest`; the known check screen saves the rest seen there.
- **Flight mapping (centred).** New `play/centre-pilot.ts`: a `CentrePilot` that owns one `LessonPilot` and, every frame, sets its assists from `Controls.flyingMode()` (the mode switch keeps working): angle -> `{control:'velocity', altitude:'hold', autoArm:true}` with caps from `input.gameSpeed` (`GAME_SPEEDS`, `KEY_TURN_DPS`), i.e. DJI Normal: sticks ask a speed, let go brakes and hovers; horizon -> `{control:'horizon', altitude:'hold'}` (own sticks, height held, idle when tipped: `UPRIGHT_MIN_COS`); acro -> `{control:'acro', altitude:'own'}` (raw throttle). Ground below by `play/ground.ts` `groundClearance` every 33 ms (as GamePilot), not lesson rays. Installed by `InputHost` in `Controls.assist` for hid and gamepad when the resolved style is centred and no lesson runs; a lesson replaces it and `setLesson(null)` puts it back. No new flight assist and no sim-core change.
- **Motor start and stop (centred).** AutoArm starts the motors on the first deliberate move (`flyingIntent`: a stick out of the 0.08 deadband or the throttle above 0.25). The radio's arm switch or the DJI start/stop button is not needed; its on->off edge stops the motors (`AutoArm.stop`); landing (hold down on the ground, `GameAssist.landed`) stops them too. A style flip while the motors run waits for the next disarm, crash or respawn (the chip says "after landing"); on the ground it applies at once.
- **Acro notice.** In centred style and acro the HUD shows one line: "Acro: the throttle is direct, the centre is half power."
- **The five places, one wording.** Names: centred = "Stick in the centre (camera drone)"; zero = "From zero (FPV)"; auto = "Automatic (by where your stick rests)". Explanations: centred = "The left stick springs to the centre: centre holds the height, up climbs, down descends. Let go and the drone stops and hovers. The motors start when you move a stick." zero = "As FPV pilots fly: the motors start (this is called arming) only with the left stick all the way down, and the stick sets the motors' power."
  - (a) Arm card: style zero, block `'throttle'`, `ch[2]` within 0.15 of the middle, still for 3 s (an estimate, to be checked on the owner's controller) -> the card adds "Your left stick is resting in the centre." "To fly like FPV, lower it all the way down: that starts the motors (arming)." and one button "Fly with the stick in the centre" (sets the profile's choice to centred).
  - (b) Controls screen, radio-in-use panel: a two-button choice (radio group) with the two names and one explanation line each, the current one pressed, "Automatic" noted under it when no choice was made.
  - (c) Settings screen: the schema row in group input, help = both explanations; deep link `?focus=input.throttleStyle`; the summary panel gets a row next to the mode chip: "Throttle: Stick in the centre".
  - (d) HUD mode chip: a second line with the style ("Stick in the centre" / "From zero"); its popover gets the two choices and the key J; J flips centred <-> zero (keymap `throttle.style`, label "Throttle: stick in the centre or from zero"); the pause menu lists J through the keymap.
  - (e) Check screen: a row "Throttle stick: rests in the centre, so you fly with the stick in the centre (camera drone)." / "... rests at the bottom, so you fly from zero (FPV)." with a button "Change to <other name>".
- **Strings** in `packages/i18n/locales/fly/` (new file `throttle/{en,es,pl,ru}.json`, plus mode-chip and arm lines); no "arm" without "start the motors". Catalogue generator rerun (README.md, llms.txt, docs/settings.md, features.json).

## DJI controllers with a screen

Web research by another agent, 2026-11-12 (confidence as stated; nothing here was measured on the owner's PC).

**What is known.**
- **DJI RC 2 (RC331)**, the 5.5-inch screen controller of the Avata 360 Fly More Combo (also sold for Mini 4 Pro, Air 3/3S, Neo, Flip; not for Avata 2). Per one working Linux bridge (rusty407/dji-rc2-linux-joystick, MIT, tested on a Mini 4 Pro RC 2): while booting it shows as 18D1:4EE7 (Google/Android vendor id), fully booted as 2CA3:1021 with three interfaces: MTP, ADB and a vendor "BULK Interface" (interface 0, bulk OUT 0x01 / IN 0x81). No HID joystick interface and no serial (VCOM) port are reported. The sticks are readable: send the DUML request `55 0d 04 33 0a 06 eb 34 40 06 01 74 24` (cmd set 0x06, cmd id 0x01) on the bulk interface; the 32-byte reply holds roll, pitch, throttle, yaw and two dials as little-endian 16-bit values, 364..1684, centre 1024. No simulator-mode packet needed; keep the drone switched off. Charge-only or C-to-C cables can stop it enumerating at all. Confidence medium.
- **DJI RC-N2 / RC-N3** (no screen, phone holder): USB identity not verified. The older RC-N1 (RC231) is a serial port "DJI USB VCOM For Protocol (COMx)": enable simulator mode with DUML 0x06/0x24 payload 01 at 115200 baud, then poll 0x06/0x01 (38-byte reply, sticks at offsets 13/16/19/22). No bridge claims RC-N2/N3. Confidence low.
- **DJI FPV Remote Controller 3**: 2CA3:1021 "DJI Virtual Joystick", a HID game controller (the owner's measurement); works today through the Gamepad API / WebHID. Its manual: Normal/Sport mode throttle self-centres, distance from centre sets the climb or descent rate; motors start with the stick combination (CSC); after landing hold the throttle down to stop them; Manual mode needs the F2 spring screw tightened (1.5 mm hex) so the stick stops recentring, then arms with the throttle at the bottom. Supports Liftoff, Uncrashed, DRL, DCL.
- **DJI RC Motion 3**: not checked.

**The browser path for the RC 2.** WebHID and the Gamepad API cannot see it (no HID interface); Web Serial cannot (no CDC/VCOM); no stick data over BLE is known. The only realistic route is **WebUSB** to the bulk interface, running the same DUML poll. Conditions: Chrome sees 2CA3:1021 after a full boot over a data cable; on Windows the bulk interface needs a WinUSB driver bound (a one-time Zadig-style install on that interface only, leaving MTP and ADB alone), because DJI ships no MS OS 2.0 descriptors as far as known, and if DJI Assistant 2 binds its own driver WebUSB cannot claim it; Linux needs a udev rule (the bridge ships one); macOS probably works without a driver (not verified). Fallback without WebUSB: a small local helper (libusb or the MIT bridge) exposing a virtual gamepad (vgamepad/vJoy, uinput) or a WebSocket; it needs the same WinUSB binding on Windows. For RC-N2/N3, if they appear as a VCOM port, Web Serial would work (not verified).

**The owner's test (before any build).** Use a USB-A to USB-C data cable (not charge-only, not C-to-C). Plug the RC 2 into the PC, power it on, keep the drone off, wait 30-60 s for it to boot. In Chrome open `chrome://usb-internals` (Devices tab) and `chrome://device-log`:
- 2CA3:1021 with an interface list (MTP, ADB, "BULK Interface" class 0xff): the route is open; next step is a small WebUSB test page that claims interface 0 and sends the DUML poll.
- only 18D1:4EE7: still booting or the cable is wrong.
- nothing: cable or port.
Windows Device Manager with "Show hidden devices" is a second view: a "Bulk"/unknown device with a yellow mark means the WinUSB binding is the missing piece.

**Not verified.** How the RC 2 enumerates on Windows (driver per interface, whether DJI Assistant 2 claims the bulk interface); whether the Avata 360's RC 2 equals the Mini 4 Pro's; whether WebUSB can claim it after WinUSB without breaking DJI Fly/Assistant; RC-N2/N3 identity; whether the RC 2 has any HID interface; DJI's exact sticks-released and landing wording for the Avata 360; any official PC-simulator mode of the RC 2.

Sources: github.com/rusty407/dji-rc2-linux-joystick (rc2link.py, 70-rc2-joystick.rules); github.com/Miniontoby/DJI_RC-N1_SIMULATOR_FLY_DCL; github.com/pverhaert/DJI_RCN1_for_drone_simulators; github.com/Matsemann/mDjiController; heliguy.com Avata 360 compatibility page; dji.com/rc-2/faq; DJI FPV Remote Controller 3 User Manual v1.0 (lensrentals.com product asset 1110698.pdf); steamcommunity and mavicpilots threads on RC 2 not showing up.

## Decisions

- S2: the WebUSB helper only lists the descriptors (`device.configurations`) and never opens the device: opening needs WinUSB on Windows and could disturb DJI's own apps; reading sticks is a later lane.
- S2: the helper is a closed `<details>` under the device choice so the four ways to connect stay first; its send action reuses the bug report form (a `message` prefill), not a new form.
- S2: 2CA3:0020 is named "the drone itself": the owner plugged the Avata 360 and saw it on the PC (measured 2026-11-09), a likely mix-up for others too.
- S2: the lesson precedence test drives the real `InputHost` with a fake context (as app-switches does) instead of a sonic lesson rig, so it does not depend on the sonic lane's files.

- Velocity control (GameAssist) for angle and height hold only for horizon, so "stops drifting" holds in DJI's N position and S stays a plain attitude mode with height hold.
- One stored truth per controller in `Profile`, the setting `persist: false` as its view, so every surface reads one store key.
- Reuse `LessonPilot` unchanged (composed) instead of a second assist or editing a sonic-adjacent file.
- Rest thresholds reused from the wizard's TUNING, no new numbers except the 3 s offer delay (estimate).
- In flight a flip waits for the ground, so a flip never drops the drone.
- J for the flip key: the only letter free in every context. Every letter is now bound; keymap.test's "free letter" control uses Digit1.
- S1: `classifyThrottleRest` lives in `calib.ts` next to TUNING (throttle-style.ts imports it): calib.ts needs it for the wizard's rest and an import back would be a cycle.
- S1: the rest seen on a connection is not written into the profile; only the wizard's centre step writes `throttleRest`. The connection watch decides first anyway, and writing on every connect would change saved profiles silently.
- S1: CentrePilot's ground is the game scheme's `groundClearance` on the scan's contact world (play/ground.ts), not the lesson's ray (a scan has no lesson walls).
- S1: the arm input in the centred style only stops the motors: an arm switch turned off, or any press of a toggle button (the DJI start/stop); after a stop the sticks must come back to the centre before a move starts them (the press is made with a thumb off a stick, the other may still be pushed).
- S1: a mode change in flight resets GameAssist and AltitudeHelp (their targets start from the craft as it is) and keeps the motors; LessonPilot is composed, not edited.
- S2: the controller's own button takes the offer: any change of its arm input (ch[4]) while the offer shows, because the DJI's start/stop is its arm toggle and the thumb already goes there; the offer hides as soon as the stick moves, so the press that arms the FPV way (stick at the bottom) never takes it.
- S2: in the centred style the arm card stays but shows one line (how the motors start) instead of the arming steps: the probe showed the "Throttle down" steps there, the very confusion the owner described.
- S2: the check screen and the Controls screen use one component (`throttle-style-row.ts`) with the setting's names and explanations; the check screen saves the rest it sees only when the profile has none (a known setup has no centre step); a rest the wizard measured is kept.
- S2: the chip, the card and the screens reuse the setting's option names (`set.input.throttleStyle.opt.*`), so the wording is one; the chip's short line is the start of the same name.
- S2: the probe flies scene 887f27aa: on 39e63ce9 both styles stop 0.29 m over the spawn (something overhead), which would hide the result.
- S1: flight tests fly over the bench's FloorWorld (tools/bench/test/game-loop.ts), not a lesson world, so they do not depend on the sonic lane's files.
