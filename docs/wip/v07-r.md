# v0.7 lane R: engine 2.23.2, SuperSplat's stochastic drawing and splat budget links

Owner's item 1 (message 18): `https://superspl.at/scene/2f1ddf5f?budget=8&stochastic`. SuperSplat's new
stochastic drawing is a beta that needs these URL parameters; the owner wants to add such links and
desktop pilots to fly with it now. Plan and contracts: [`v07-plan.md`](v07-plan.md).

## What SuperSplat does (read 2026-10-13, `@playcanvas/supersplat-viewer` 1.37.0, MIT)

- `budget`: `Number(url.searchParams.get('budget'))`, millions of splats; used when finite and > 0, else
  the viewer's own: desktop 4 M (2 M in its performance mode), phones and tablets 2 M (1 M).
- `stochastic`: `url.searchParams.has('stochastic')`, so any value turns it on (even `stochastic=0`).
- Stochastic only on WebGPU (`renderer === 'webgpu'`) and not in XR; on WebGL the sorted renderer draws.
  It is also refused when the budget does not fit the device's storage-binding limit. The viewer itself
  does not refuse phones; "desktop only" is what the owner sees on superspl.at.
- The viewer 1.37 draws stochastic with its OWN renderer (`src/render/stochastic-splat-renderer.ts`,
  about 3,500 lines of TypeScript and WGSL: compute projection, unsorted raster, temporal accumulation
  that removes most of the dither noise). The engine 2.23 has a smaller built-in mode:
  `app.scene.gsplat.stochastic` (GPU-sort renderer on WebGPU only, unsorted, dithered coverage against
  blue noise by default, opaque blending, depth writes, no temporal accumulation).

## What we do

We use the engine's built-in mode (the owner's brief and the plan name it; porting SuperSplat's
3,500-line renderer is a separate decision, see "Honest limits"). Rules:

- **Links.** `packages/scenes/src/link.ts` (new, pure): `parseSceneLink(raw) -> { id, render? }` reads a
  bare id, `superspl.at/scene/<id>?...` and `superspl.at/s?id=<id>&...`; `render.budgetM` from `budget`
  (finite, 0.25..32 M, the contract's range; anything else dropped), `render.stochastic` from
  `stochastic` (present with no value, `1`, `true`, `yes`, `on` -> true; `0`, `false`, `no`, `off` ->
  false, an explicit "sorted"; any other value dropped). Deviation from SuperSplat on purpose:
  `stochastic=0` means off here. `parseSceneInput` keeps its signature (the id) and calls it, so no
  caller in another lane breaks. The fly deep link `/fly/?scene=<id>&budget=<M>&stochastic`:
  `writeSceneQuery(q, id, render?)` writes `scene`, `budget` and `stochastic` into a `URLSearchParams`
  (and removes a stale `budget`/`stochastic`), `flyQueryString(q)` serialises it with the bare
  `&stochastic` flag, `flyDeepLink(flyPath, id, render?)` does both for a whole link (e.g. `/en/fly/`).
  `renderParams(budget, stochastic)` reads the two raw values (a page's own query).
  `sceneRender(link, catalogue)`: the link's fields win, the catalogue's `render` is the default.
- **Where a link is pasted.** The picker's field and its tabs hand the raw text on (not only the id);
  the page's boot reads the scene value's own parameters and the page's `budget`/`stochastic`; the
  landing's ScenePaste already passes the whole link in `?scene=` (no change needed, comment updated);
  the admin's add field stores the link's `render` in the new catalogue entry (contract field).
- **Policy (pure).** `packages/render-pc/src/drawing.ts`: `resolveDrawing(mode, request, device)`
  (positional) with mode = the Display setting `display.drawing` (`auto` = what the link or catalogue
  asks, `stochastic`, `sorted`), request = `{ budgetM?, stochastic? }`, device = `{ webgpu, handheld }`.
  The request applies only on desktop WebGPU; on phones/tablets
  (`isHandheld(ua, touchPoints, uaDataMobile)`: Android, iPhone/iPad, iPadOS's Mac UA with touch) or
  WebGL it is ignored and the result carries a note key `<who>-<why>` (`DrawingNote`): who asked is
  `scene` (its link or the catalogue, setting on auto), `setting` (the pilot chose stochastic) or
  `budget` (only a non-default budget was refused, nothing about stochastic); why is `handheld` or
  `webgl`. Texts `drawing.note.<note>` in en/es/pl/ru; the budget notes quote `{budget}` and `{top}`.
  `applyDrawing(params, stochastic, gpuSort)` is
  the only place that writes `stochastic` to the engine (tested with a fake params object).
- **Governor.** The budget becomes the governor's top level: `FrameGovernor` keeps its five steps as
  shares of a top budget (default 4 M, so nothing changes without a link) and `setTopBudget(m)` scales
  them. Missed frames lower the budget and the render scale as before; stochastic stays on.
  The pilot's quality slider and cinema mode scale with the same top.
- **Engine upgrade** 2.22.4 -> 2.23.2 in `apps/fly` and `packages/render-pc`: `lodMode` is deprecated
  (LOD is always by distance now) and goes; `splatBudgetMode = GSPLAT_BUDGET_TARGET` is set explicitly
  (the engine default, the same meaning the budget had in 2.22).
- **Display setting** `display.drawing` in `packages/prefs/src/defs/display.ts` (global, live, default
  `auto`, no schema bump), texts in `packages/i18n/locales/fly/drawing/*.json` (en, es, pl, ru).
- **Test hook.** `window.__gsfpv.drawing` (written by `apps/fly/src/app/builtin/drawing.ts`, read by the
  benches) = `{ scene, mode, request, stochastic, budgetM, note, engineStochastic, engineBudgetM,
  handheld, webgpu }`.

## Honest limits (filled in with the measurements)

Machine: i9-7980XE, Chrome 155, the owner's 4K monitor at 30 Hz over HDMI (every drawn rate below is
capped at 30 Hz, so fps cannot tell the two drawings apart here). Release builds under the enforced CSP.

- **Upgrade 2.22.4 -> 2.23.2.** `accept-fly` B6 B7 B9-B16 pass before and after
  (`evidence/2026-10-13/b-fly-*-v07r-{before-2224,after-2232}.json`). `v05-latency` sorted, 39e63ce9
  (`v05-latency-v07r.json`): stick -> screen estimate p50/p95 84.5/95 -> 85.6/97 ms (governor on) and
  82.8/94.6 -> 88/97.8 ms (governor off); presentation p50 48 -> 56 ms in both pairs. A small later
  frame (up to a quarter of a 33 ms period) is possible and not explained; p95 moves by 3 ms or less.
  The in-flight GPU frame cap still works: under a 40 ms GPU hog, cap 2 gives presentation p50/p95
  80/136 ms, the no-cap control 144/176 ms. The 60 Hz recording passes with stochastic on
  (`v03-rec-R1-v07r-stochastic.json`: 600 frames, 0.7 % repeated).
- **What stochastic looks like.** Dither grain: every splat is drawn opaque or not by a blue-noise
  threshold, so soft edges, walls and lamps get a fine speckle (`v07-render/look-*.jpg`; R5 fine-detail
  energy 0.0095 sorted vs 0.040 stochastic). With a still camera the grain stands still (two stochastic
  frames differ by 2e-5); in motion the pattern moves with the picture (expected, not measured). The engine has no temporal accumulation, so it is
  noisier than SuperSplat's own viewer, which smooths the grain over frames.
- **Does it help.** GPU time per frame on 2f1ddf5f (259 M splats at full detail), governor off, the
  engine's GPU profiler, p50 over 10 s in two alternating runs each: 1280x800 at 8 M, sorted 6.0/2.8 ms,
  stochastic 5.1/10.0 ms (no difference beyond the run-to-run spread); 3840x2160 at 32 M, sorted
  10.3/9.4 ms, stochastic 6.0/7.7 ms (about 25-40 % less: no sort passes). Stick -> screen on the same
  scene at 8 M: sorted p50/p95 88/98 ms, stochastic 81/97 ms (about a quarter period sooner at p50, same
  p95). So: on this PC it helps only when the budget and the resolution are high; at the default window
  it costs grain for no measurable gain. On a 60+ Hz display the GPU saving may show as fps; not measured.
- **Not covered here.** A real phone and a real WebGL-only browser (the gate is tested with an Android
  user agent in Chrome and with unit tests); Safari/Firefox WebGPU.
