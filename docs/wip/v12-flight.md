## Rules

- Commit locally, one commit per step, with the Status line of that step ticked in the same commit. Never push, deploy, SSH or log in to the live admin.
- Never edit the submodule or `C:/dev/ShramkoSonicFPV`. A change needed there goes under "Needs from sonic-core" below (reason and a failing test) and you work around it with a local adapter.
- Every hook you add is a no-op while the sound mode is off, so ordinary flight is unchanged: `tools/bench/test/a6-reference.test.ts` keeps its hash at default settings.
- A step runs only the checks its change touches, plus a negative control where it proves something; the lead runs every gate once before release. Browser runs are headless through `tools/bench/src/chrome.mjs` and hold `C:/dev/.gpu-lock` when they draw; local site checks use `SITE=http://localhost:<port>`. Long logs go to files.
- Texts for people only in `packages/i18n/locales/**` (en, es, pl, ru); Cyrillic or Polish letters outside locales fail B18 (write `\uXXXX` in tests).
- Every number you report is measured or labelled an estimate. How a sound feels cannot be judged by an agent: say so.
- Replay markers (plan section 9.5): the host emits a `lesson open` event, `key` events with the action `reset.checkpoint`, `reset.start` or `next`, and a `speech` event with the key `speech.end` whenever it calls `runner.spoken(t)`; it passes `say.interrupt` to speech and sends `setLayers({ on: [] })` when frames stop. Emit them as `sonicEvent`; the feedback lane records them.

- How a lesson runs in the page: `?sonic=` -> `sonic/start.ts` (start screen, the press makes the AudioContext) -> `boot.ts` launch -> `fly()` on the lesson's built-in world -> the feature `app/builtin/sonic-flight.ts` installs the mode, the engine hook, `ctx.sonic`, the lesson host (`sonic/lessons.ts`, `lessonHost(ctx)`) and opens the entry's lesson. `host.open(id)` swaps the flown session when the walls differ (`entry.swapSession`, set by `fly()`), draws the helper's view, makes the runner with the saved progress and enters the mode. A scan lesson goes through `LessonPage.scanLesson(lesson)` (step 10): the page brings the scan to the lesson's size (it already flies it when the entry loaded it, else `ctx.scenes.load` in place of the lesson world's session, with `scene.transform` and `scene.walls` forced in the prefs' session layer), then `buildScanLesson` gives the world over `session.collision` and the track, the gates, the start and the floor; `start.ts` launches a scan lesson with `world: null`, the scene id and the forced prefs.
- The mode clock: `mode.bridge.now()` (whole ms since `enter()`; each lesson is a new `enter()`, so a new clock and, for the replay, a new package: the replay core says a package is one lesson); every `sonicSample.t` and every event the bridge sends use it. The bridge sends 'session' pause and resume; the recorder should not write them again. A paused flight is not stepped by the host (the recorder keeps no paused frames either: FlightFrame has no paused flag).
- Keys: `ctx.keys.on` runs the LAST handler registered for an action. The feature registers Z (`sonic.repeat`), I (`sonic.status`: the lesson line, `lessonHost(ctx).status()`) and G (`sonic.glossary`); the recorder lane's feature installs after it and owns T and U. If it registers I as well its handler wins: it should say the lesson line and then its own recording status (`status.recording-on` or `-off`).
- The recorder (lane v12-feedback) reads `ctx.sonic` (live), `sonicSample` and `sonicEvent`; the host's markers (`lesson open`, `key` reset.checkpoint / reset.start / next, `speech.end`) come through the bridge and a lesson flown through the host passes the package's `checkSession` (tools/bench/test/sonic-lessons.test.ts). `ctx.hook.sonic(withEvents?)` is the test hook (lesson, phase, attempt, craft, question, progress, the last 600 events).
- Contacts with the respawn platform are not touches (`onPlatform` in sonic/bridge.ts): found in step 9, a restart parked the craft on the invisible disc and its settling counted as a touch, so every attempt after a restart began with one (a lesson that allows none could never be passed after its first attempt).
- The page chrome of a scan (the credit line with the walls switch) is hidden by `body.sonic-mode` (sonic.css); the rest of the page is the normal flight page, so the walls box's top-middle offers ("Refine walls to 1.6 cm") and the pause menu's scene items are still there for a helper in a scan lesson. While the mode runs the prefs' session layer holds `scene.transform` and `scene.walls` for ANY scene (the layer has no scene key): a helper who changes the scan from the pause menu during module 7 gets the new scan at x5 with walls on.
- Step 10 and 11 for the next agent: the track is version 1 and not yet published; a change after the release is a new file (`...-v2.json`, parent `7a475d38-rings` 1) and the lesson's `track.version` is the package's (a "Needs from sonic-core" change then). The check tool and the rig run on the walls in `.cache/scenes/7a475d38` (CDN files, 19 MB); without them the tests of that part skip. The replay of a scan lesson (recorder lane) needs the gates and the start: `ctx.sonic.world.objects()` gives the gates in the flown world, the start is the track's (flown through the transform), the manifest's `track` names the file. `ctx.scenes.load` (the in-page switch) also records the scan in the pilot's scene history and sends the `scene_switch` beacon.
- Found, not changed (not my files): `apps/fly/src/walls.ts` reads the flown cell size as the shipped walls' resolution (`shipped.voxelM = s.collision.voxelResolution`), so at any scene size other than x1 its refine plan is wrong (at x5: 263 M predicted nodes, refused). A fix is one line (the base grid's resolution, `session.baseCollision`), and it would let a refine made at x1 be found at x5; whoever owns walls.ts should read the numbers under "8.6" in step 10 first: the page's refine took 417 s here for Winter Garden, not the 62 s it estimates.
