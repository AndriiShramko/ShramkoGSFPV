## Design note

### 1. Three new drone presets (only new ids; the default drone stays `pavo20pro-3s`)

- Research first, with sources: which cinelifter, 5" racing quad and 5" freestyle quad pilots actually fly most
  today, and their published numbers (all-up weight with battery, with the camera for the cinelifter, frame
  geometry, motor size/KV, props, battery, thrust-to-weight, Betaflight rates/filters where published, how they
  fly). Written to `docs/research/drones-v08.md`; every preset field keeps its own `source`
  (`manufacturer`, `measured:<who>`, `estimate`, `bf-default`) and `ref`, as the six existing presets do.
- Presets are JSON files in `packages/sim-core/presets/` with exactly the existing field set (so
  `compileParams` needs no change to read them); `DRONE_IDS` (`packages/prefs/src/defs/drone.ts`),
  `apps/fly/src/presets.ts` and the preset lists in tests grow by three ids. The generated catalogue
  (`scripts/gen-catalog.ts`) shows them on the landing, in `docs/settings.md` and README.
- An X8 cinelifter (coaxial pairs) is flown by the same quad-X model: each arm is one thrust point carrying
  the pair; the coaxial loss is inside the stated thrust-to-weight, the pair's reaction torque cancels mostly
  (a lower `motor_kappa_m`), the two rotors' inertia adds (`rotor_inertia_kgm2`).
- Physics that tells the three apart, from the existing model's parameters: mass and inertia (the camera on
  the cinelifter's nose and its 8"-10" arms: large roll/pitch/yaw inertia), motor lag (big motors and props:
  `motor_tau_ms` 40-60 ms against 15-20 ms on a 5"), thrust-to-weight (cinelifter about 2.5-3:1 with the
  camera, freestyle 7-9:1, racing 10-14:1), battery sag (6S/12S packs under large current: pack resistance),
  open-prop rotor drag (`rotor_drag_per_s`, momentum theory scaled like the existing presets), body drag
  (`cda_*`: a racer is slimmer than a freestyle quad with a GoPro), PIDs/rates/throttle where the maker or a
  well-known tune publishes them.
- Prop wash: the model today has no loss of thrust when the craft sinks into its own wake. A new optional
  preset field (`wake_loss`, absent = 0 = the model of today bit for bit, so the six presets and the A6 hash
  do not change) takes away part of the thrust while the rotors descend through their own downwash (axial
  descent between about 0.3 and 1.5 of the hover induced velocity, the vortex-ring region of momentum theory),
  with the induced velocity computed from the disk area of the preset. Deterministic (no random numbers);
  heavy craft with low thrust-to-weight and slow motors feel it most, as in real life.
- Unit tests per new preset, each with a negative control: thrust-to-weight at full throttle, hover
  throttle in its expected band, maximum climb rate, roll rate (time to reach the rate setpoint: the
  cinelifter is clearly slower than the 5"s), racing faster than freestyle in top speed, the wake loss
  absent on the old presets (A6 hash unchanged) and present on the cinelifter.

### 2. "Help us tune this drone"

- One message, the same everywhere: the presets are estimates from published numbers; if you fly this drone
  for real and the physics feels wrong, send the owner your Betaflight `diff all`, a link to a blackbox log
  of a flight, your rates and a few words; or ask to add a drone that is missing.
- Where: the drone picker (a line on top + a "Help us tune it" button on each card), the settings screen's
  drone group (a line + button), the feedback dialog (a fourth kind "Drone physics"), the landing (the drones
  block of the settings catalogue: a note and a "Help tune it" link per drone; one FAQ answer), docs
  (`docs/settings.md` via the catalogue, `docs/research/drones-v08.md`, README FAQ through the catalogue).
- The form (simulator, `apps/fly/src/app/builtin/feedback.ts`, kind `drone`): which drone (the one flown is
  preselected; "a drone that is not in the list" for a new one), what feels wrong / which drone to add,
  `diff all` pasted as text (optional, up to 100 000 characters), a link to the blackbox log (optional),
  e-mail. Sent with it: the drone id and the pilot's own simulator settings for that drone. Deep link
  `/{lang}/fly/?drone=<id>&open=tune` (the landing's links) opens it.
- API (`apps/api/server.py`): `POST /api/report` takes `kind: "drone"` with whitelisted fields (`drone`,
  `betaflight`, `logUrl`, `settings`). The Betaflight text and the settings are stored as the report's
  technical-details file (`reports/<id>.json`, the same file a bug's diagnostics use), so the admin's
  download, the Telegram document and `tools/reports/pull.py` work unchanged. The report becomes an idea in
  the ideas store whose text starts with what the owner needs at a glance (drone, log link, whether a diff
  is attached); the owner answers from Gmail as for any idea.
- Texts: `packages/i18n/locales/fly/tune/{en,es,pl,ru}.json` (own namespace: no conflicts with other lanes'
  keys), the site dictionaries for the landing, the bot dictionary only if a new card line is needed.
