# v0.11 lane N: does N wrap on the live site? (the owner's item 9, message 22)

Branch `v11-n`, base `b316bce`. Question from the reels agent: on the LIVE site (release `5e61039a46d3`, 13 published
scenes) N "wraps back to the first scene (887f27aa Tunis) instead of going on into SuperSplat". The v0.9 lane
([v09-n.md](v09-n.md)) built the tour and tested it only against a mocked `/api/catalog` and `/api/superspl/explore`.

## 0. Verdict

**It does not wrap when the walk starts on the first scene: 12 presses go through the other 12 catalogue scenes in the
admin's order, the 13th goes into SuperSplat, and so on.** Seen with the scan not drawn (A), drawn (B, two final runs), and
on a local release of this tree fed with the live answers (G): the same 16 scenes each time, no failed load, no write to the
site other than the page's own beacons (answered here). One of four drawn runs logged 8 WebGPU page errors during scene
switches; the sequence was not touched (section 5).

The reels agent's observation is real, though, and two things produce exactly it. Neither is a defect of the tour:

1. **The walk starts where the page opened.** A scene on screen is "seen"; N brings the first UNSEEN scene after it, round
   the list; SuperSplat starts only when every catalogue scene was seen once (decision D63: "go through all of HIS
   scenes, then SuperSplat"). A page opened on `b11e45d1` (the LAST scene of the live list, "yamato koriyama castle")
   gets `887f27aa` (Tunis, the first) from its first N; a page opened in the middle goes round the end of the list to
   Tunis and meets SuperSplat after the 12th press, not after the last scene. Every page load starts a fresh walk (D64).
2. **SuperSplat did not answer** (down, 503, or later than the 4 s budget of D66): the step says "No new scene to bring right
   now: the author's list starts again." for 4.5 s and begins a new round, which from `b11e45d1` is `887f27aa` again. Only
   that line tells it from case 1, and it is gone by the time a screenshot is taken. After it the next SuperSplat try comes
   12 presses later (the round walks the catalogue again first).

The live proxy answered every real request: `GET /api/superspl/explore?sort=trending&order=-1&time=all&features=walkable&skip=0&limit=24`
(the tour's query) = 200 in 0.16 to 0.9 s (cold 0.88 s, `x-cache: miss`; warm 0.16-0.47 s), 1532 walkable scenes. The
agent's own probe used `sort=starred`, a different query (also 200, 0.48 s), which says nothing about the tour's.

## 1. How it was run (read-only, headless)

`tools/bench/src/accept-v11-n.ts` (new): the bench's headless Chrome (`launchChrome`, never `BENCH_VISIBLE`), a fresh
context per run, `?scene=<id>&nowarn=1&render=off|on&input=touch` (no warning card, touch input so no Controls screen:
the same options as `accept-v09-next`), `localStorage gsfpv_consent=no` before the page runs (no consent card, nothing to
Google). One route in the context: the page's own `POST /api/e` beacons are answered with 204 here, any other write is
aborted and listed (`blockedWrites`: empty in every run), everything else is a plain GET to the live site. Each press: from

note, the tour's `seen` set, the SuperSplat requests with status and time. `SS=abort|503|slow` stands in for a proxy that is
down, busy or slow (nothing is sent to the live site for it); `FEED=live` runs a local release with the live answers fetched
with a GET; `CRASH=1` adds the scene after a crash.

## 3. Not the cause (each checked)

- the filters: the walls flag never filters the owner's catalogue (v0.9 root cause, fixed); all 13 are in the walk, 9 of them
  without a walls file; `hidden` scenes are not in the API's answer;
- the remember/order defaults: nothing is stored between visits (`gsfpv.tour.v1` is never written), `scenes.order` unset is
  "in order" for the catalogue;
- a query the live proxy rejects: the tour's query is a 200 (above); CSP: the fetch is same-origin and succeeded in the
  real page; an error swallowed: none, no scene failed to load in any run and the page logged no `pageerror` in any run but
  the one of section 5, which did not touch the sequence;
- the 4 s budget: the live proxy needs 0.16-0.9 s, so it ends a step only for a proxy that is really slow or down (E);
- the failed-scene list: no scene failed to load, drawn or not;
- the 403s in the browser console (19 per run): the CDN's answer for optional files a scene does not have
  (`settings.json` v1-v6, `meta.json`, `lod-meta.json`, `scene.voxel.json`; S3/CloudFront answers a missing key with 403): the
  loader probes them; `httpErrors` in the evidence lists them by path, none is an API answer.

## 4. Decision: no code change

The tour does what D63 says. No deploy, no restart, no migration. This lane adds only the bench check and its evidence.

Not checked: the owner's own browser profile (a stored `scenes.rotation` of favourites or history, `scenes.order` random, a
changed walls filter, a failed-scene list: N then walks his own list or a shuffle, and a "wrap" there is the old rotation
code's, packages/scenes `rotation.ts`); only fresh profiles were run. A real touch phone, a slow mobile connection (the 4 s
budget on a bad link is the case E). A reload between presses (each load of the page starts a fresh walk, D64, so a capture
that reloads `?scene=<last>` for every take always sees the first scene next).

## 5. Side finding, not this lane's (reported, not touched)

One of the four drawn runs on the live site (the second; its evidence file was overwritten by the third run of the same label,
so only this text remains) logged 8 page errors while the scenes switched: three
`Failed to execute 'createBindGroup' on 'GPUDevice': ... The provided value is not of type 'GPUBufferBinding'` and five
`Cannot read properties of null (reading 'createView')`: the renderer drawing a frame with a buffer/texture of a session that
was just disposed (`SceneHost.load` disposes the old session and starts the new one on the same renderer). Every switch of that
run still ended `done`, the sequence was the same as in the other runs, and the other three drawn runs (and every run with
the scan not drawn) logged none. Per-press page errors are recorded now (`presses[].pageErrors`), so a next occurrence says which
press it was. It is a candidate for whoever owns `session/` and the renderer swap; it does not touch the order of N.
