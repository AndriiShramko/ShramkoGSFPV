# v0.11 lane N: does N wrap on the live site? (the owner's item 9, message 22)

Branch `v11-n`, base `b316bce`. Question from the reels agent: on the LIVE site (release `5e61039a46d3`, 13 published
scenes) N "wraps back to the first scene (887f27aa Tunis) instead of going on into SuperSplat". The v0.9 lane
([v09-n.md](v09-n.md)) built the tour and tested it only against a mocked `/api/catalog` and `/api/superspl/explore`.

## 0. Verdict

**It does not wrap when the walk starts on the first scene: 12 presses go through the other 12 catalogue scenes in the
admin's order, the 13th goes into SuperSplat, and so on.** Seen with the scan not drawn (A), drawn (B, two final runs), and
on a local release of this tree fed with the live answers (G): the same 16 scenes each time, no failed load, no write to the
site other than the page's own beacons (answered here). One of four drawn runs logged 8 WebGPU page errors during scene
switches; the sequence was not touched (section 5).

The reels agent's observation is real, though, and two things produce exactly it. Neither is a defect of the tour:

1. **The walk starts where the page opened.** A scene on screen is "seen"; N brings the first UNSEEN scene after it, round
   the list; SuperSplat starts only when every catalogue scene was seen once (decision D63: "go through all of HIS
   scenes, then SuperSplat"). A page opened on `b11e45d1` (the LAST scene of the live list, "yamato koriyama castle")
   gets `887f27aa` (Tunis, the first) from its first N; a page opened in the middle goes round the end of the list to
   Tunis and meets SuperSplat after the 12th press, not after the last scene. Every page load starts a fresh walk (D64).
2. **SuperSplat did not answer** (down, 503, or later than the 4 s budget of D66): the step says "No new scene to bring right
   now: the author's list starts again." for 4.5 s and begins a new round, which from `b11e45d1` is `887f27aa` again. Only
   that line tells it from case 1, and it is gone by the time a screenshot is taken. After it the next SuperSplat try comes
   12 presses later (the round walks the catalogue again first).

The live proxy answered every real request: `GET /api/superspl/explore?sort=trending&order=-1&time=all&features=walkable&skip=0&limit=24`
(the tour's query) = 200 in 0.16 to 0.9 s (cold 0.88 s, `x-cache: miss`; warm 0.16-0.47 s), 1532 walkable scenes. The
agent's own probe used `sort=starred`, a different query (also 200, 0.48 s), which says nothing about the tour's.

## 3. Not the cause (each checked)

- the filters: the walls flag never filters the owner's catalogue (v0.9 root cause, fixed); all 13 are in the walk, 9 of them
  without a walls file; `hidden` scenes are not in the API's answer;
- the remember/order defaults: nothing is stored between visits (`gsfpv.tour.v1` is never written), `scenes.order` unset is
  "in order" for the catalogue;
- a query the live proxy rejects: the tour's query is a 200 (above); CSP: the fetch is same-origin and succeeded in the
  real page; an error swallowed: none, no scene failed to load in any run and the page logged no `pageerror` in any run but
  the one of section 5, which did not touch the sequence;
- the 4 s budget: the live proxy needs 0.16-0.9 s, so it ends a step only for a proxy that is really slow or down (E);
- the failed-scene list: no scene failed to load, drawn or not;
- the 403s in the browser console (19 per run): the CDN's answer for optional files a scene does not have
  (`settings.json` v1-v6, `meta.json`, `lod-meta.json`, `scene.voxel.json`; S3/CloudFront answers a missing key with 403): the
  loader probes them; `httpErrors` in the evidence lists them by path, none is an API answer.

## 7. Second phase, B: the WebGPU page errors during scene switches (the lead's task B)

**Plain use does not reproduce it.** On the base build (`b316bce`), headless, drawn, `FEED=live`, with the owner's accumulating stochastic as the desktop
default (`drawing.drawn` = `accum`, class `desktop-strong`): **392 scene switches, 0 page errors, 0 WebGPU validation errors** (`v11-n-b-*.json`, the counts are
the sum of `presses` per file; the runs with FUZZ or FAULT are not in it): the owner's 13 scenes cycled 229 times (120 of them with three Chromes drawing
on the GPU at once), the real catalogue and then SuperSplat's scenes 103 times, 30 with a random render scale and splat budget every 120 ms (the calls the
quality governor makes) and 30 with a second page drawing a big scene and JavaScript 3 times slower; no pause between switches in all but 46. The event of the
live run (8 errors, one run in four) did not come back, so its trigger is NOT identified.

**What does reproduce is the mechanism, and the live burst has its signature.**

1. *The state.* The vendored `detach()` (the hand-back to the sorted drawing at `unloadSplat`) destroys the renderer's view (targets, textures, buffers) and
   puts an empty one in its place, but leaves the pass flags as the last frame set them. The switch timeline (`TIMELINE=1`, `v11-n-b-timeline2.json`) shows it
   while the drawing is held: raster pass enabled, taa pass enabled, compose visible, view bindings 0, no resident set. The passes and the compose take their
   render target and textures from the view's bindings, which only a frame of the renderer writes. In normal use the hold ends only when the new scan has
   drawn, a frame follows at once, and the engine never sees that state.
2. *Attached again before a frame has bound a view* (a drawing asked for while the scan loads, or a frame function that throws first), the engine starts the
   raster pass on the destroyed target: `Cannot read properties of null (reading 'createView')` out of `startRenderPass -> initRenderTarget`, which no guard
   covers (the guards wrap `execute`), on every frame until a frame binds a view.
3. *Reproduced two ways, same message and the same state (enabled, passes on, no bindings, no resident set) at the first error of every burst:*
   - `FUZZ=toggle`: the drawing switched between stochastic and sorted at random moments (30 to 400 ms) during N presses; each toggle is a call REC, the video
     export, the share picture or the pilot's Render setting make. **Base: 14 of 40 switches threw, 557 page errors** (`v11-n-b-base-fuzz-40.json`; two more
     runs: 6 of 25 switches, 58 errors; 6 of 40 with governor stress, 97 errors). Cause: `unloadSplat` held the accumulating renderer only if it was DRAWING at
     that moment, so a stochastic request during the load (the next scene's, the pilot's, the end of a recording) attached it with no scan.
   - `FAULT=first-frame`: the page's own `forceFault` hook makes the renderer's frame function throw the first time it should run after being attached during
     a switch. **Base: 4 of 4 page loads, 5, 6, 6 and 6 page errors spanning 230 to 260 ms**, all `reading 'createView'`, the guard's console error once
     (`v11-n-fault-base-*.json`). Cause: a throw at a guarded site defers the hand-back to the frame's end; the engine's render threw, the frame never ended, the
     250 ms timer handed back, and every frame in between threw again. 250 ms at 25 to 30 frames a second is the 8 errors of the live run. The live run's two
     messages were `createBindGroup ... GPUBufferBinding` (3) and `createView` (5); only `createView` was reproduced, so that the live burst was this one is
     consistent with the evidence but not proven.
4. *Fix (render-pc; no vendored file touched):* `accum.ts quietRenderer()` leaves a detached renderer quiet (`setReady(false)`, taa pass off: the state it is made
   in) after every hand-back and at once when a guarded site throws; `accum-policy.ts holdOnUnload()` keeps the accumulating renderer out of the next scan
   whether or not it was drawing at the unload (`renderer.ts unloadSplat`). Unit tests (`accum.test.ts`, `accum-policy.test.ts`): the stand-in keeps the one
   vendored behaviour that matters (detach leaves the flags; only `setReady` changes them); the two behavioural tests of the quiet state fail with the old `accum.ts`,
   the quiet-at-fail one fails without its line (each checked by putting the old code back).
