# v0.7 lane B — the ideas server (design note)

Owner's items 3, 7 and 8 of message 18 (server side), plan `docs/wip/v07-plan.md`. Plus the owner's
words relayed with this lane: every pilot's data goes straight into his Telegram chat too (the whole
report, not a short note).

## What changes and why

Today a report (`POST /api/report`) is a line in `reports.jsonl`, a short note to the shared lead bot
(`TG_BOT_TOKEN`, used by every site on the hub; nothing reads its updates), an open/closed flag in the
admin and a local status file of `tools/reports/pull.py`. Nothing can answer a pilot, nothing remembers
what the owner decided, and the landing's roadmap is a hand-written list. The lane turns this into one
store with one set of use-cases, reached from four places: the owner's own Telegram bot, the admin, the
agents' tool over SSH and the public roadmap.

## Structure (apps/api/, stdlib only, every module documented at its top)

| Module | Job | Knows about |
|---|---|---|
| `ideas.py` | the store `DATA_DIR/ideas.json`: ideas, their e-mail thread (the outbox lives inside each idea), Telegram message map; migration from `reports.jsonl` + `report-status.json`; the roadmap seed; queue order; the public roadmap (ETag). Durable writes (temp file, fsync, rename) under a thread lock and a file lock (the CLI runs in another process) | files only |
| `texts.py` | the bot and e-mail texts: `packages/i18n/locales/{bot,mail}/<lang>.json` (on the hub copied next to the API as `api/locales/{bot,mail}/`) | files only |
| `mailer.py` | composing an e-mail in the pilot's language (text/plain + simple HTML, quote, signature, Message-ID / In-Reply-To / References) and the SMTP transport (smtp.gmail.com:587, STARTTLS, `GMAIL_USER` + `GMAIL_APP_PASSWORD`) | texts |
| `outbox.py` | the worker thread: sends due e-mails one at a time, `queued -> sending -> sent`, retry with backoff, never twice (a `sending` found after a restart becomes `unknown`, never resent by itself) | store, mailer, a notify callback |
| `service.py` | the use-cases, the only code that changes an idea: add a report or a note, status, urgency, comment, public title/text/visibility, release link, reply by e-mail (60 s undo), cancel, done summary -> draft, explicit send of the draft | store, mailer |
| `ownerbot.py` | the owner's bot (`TG_OWNER_BOT_TOKEN`, by default the shared `TG_BOT_TOKEN`: the owner's decision 2026-10-13, no new bot): Telegram API client, the report card with buttons (and the diagnostics file and picture), the webhook (secret path + `X-Telegram-Bot-Api-Secret-Token`, only the owner's chat), commands `/note /queue /help`, replies, buttons | service, texts |
| `ideas_admin.py` | `/api/admin/ideas...` routes (wired into `admin.py`'s session + CSRF) | service |
| `ideas_cli.py` | the agents' commands inside the container (`docker exec -i gsfpv-api python /app/ideas_cli.py ...`): queue, show, status, title, summary, comment, release, webhook setup, Gmail login check | service, ownerbot |

`server.py` only wires them: `POST /api/report` stores the line (unchanged), then adds the idea and
delivers it (owner bot with buttons when configured, else the shared bot as today, now with every field);
`POST /api/tg/<path>`; `GET /api/roadmap`. `tools/reports/pull.py` is replaced by `tools/ideas/ideas.py`
(same `pull`/`list`/`show --log` for reports plus the queue and the agents' commands; UTF-8 stdout).

## The idea record

`id` (`R-YYYYMMDD-NNNN` from a report, `N-...` a note, `F-...` a roadmap feature), `kind`
(`idea|bug|note|feature`), `created`, `text` (the pilot's words, private), `lang`, `page`, `scene`,
`release`, `contact`, `contactKind` (`email|other|none`), `email` (the address found in the contact),
`suspect`, `diagnostics`, `status` (`new|accepted|in_progress|done|rejected`), `statusAt`, `urgency`
(`low|normal|high|urgent` or null), `comments` `[{at, text, by}]`, `public` `{title: {lang}, text: {lang},
visible}`, `done` `{at, summary: {lang}, by}`, `notified` (when the thank-you e-mail went), `releases`
`[sha]`, `thread` (e-mails: `{id, kind: reply|done, to, lang, subject, body, plain, html, messageId,
inReplyTo, references, state, created, notBefore, attempts, nextAt, error, sentAt, by}`; states `draft`,
`queued`, `sending`, `sent`, `failed`, `cancelled`, `waiting_setup`, `no_email`, `unknown`), `order`
(features), `source` (`report|telegram|admin|seed`).

Migration: the first load imports every line of `reports.jsonl` (suspects too, flagged) and maps the old
admin flag (`open` -> `new`, `closed` -> `done`); every later load imports any report line still missing,
so a report stored while the store failed is never lost. `reports.jsonl` itself is never rewritten.
The old admin routes `GET /api/admin/reports` and `POST /api/admin/reports/status` keep their shape and
read/write the store. The roadmap seed (`apps/api/roadmap-seed.json`, lane C) is loaded once, the first
time the store has no feature and has never been seeded.

## Rules the code enforces

- No e-mail leaves without the owner's explicit act: a reply to the card (then a 60 s window with Cancel),
  or Send under a draft. The done e-mail is only ever a draft until Send. The CLI and agents never send.
- Owner's decision 2026-10-13 (overrides the first brief's dedicated bot): no new bot. The two-way work
  runs on `TG_OWNER_BOT_TOKEN`, default the shared `TG_BOT_TOKEN`, and is on when `TG_WEBHOOK_SECRET` is
  set; without the secret every report goes to the shared bot as plain text exactly as before plus every
  field the pilot sent (the owner's request), no buttons. `tg-setup` never replaces another service's
  webhook on the bot unless `--replace`.
- The shared bot's webhook carries every update of that bot. Only the owner's chat is obeyed
  (`TG_OWNER_CHAT_ID`, default `TG_CHAT_ID`), and in it only what is GSFPV's: its commands, a reply to a
  bot message the store mapped to an idea, a button whose idea/e-mail id the store knows (`_ours`, read
  only). Everything else (a reply to another site's lead note...) gets 200, no answer, no write.
  Each GSFPV update is handled once (its id is kept with the change it made).
- Gmail not configured -> the e-mail waits in `waiting_setup` and the bot says so; once configured the
  bot asks per waiting e-mail (Send / Cancel), nothing goes by itself.
- The roadmap shows only items with an English public title, status accepted (as `planned`),
  in_progress or done, and `visible` not false; it never carries text, contact or anything the pilot wrote.

## Contracts for lane C (admin kanban, landing roadmap)

- `GET /api/roadmap` (public, ETag/304, `max-age=60`): `{"v":1,"items":[{"id","kind":"feature|idea|bug",
  "status":"planned|in_progress|done","title":{"en",...},"text"?:{...},"fromPilot":bool,"done"?:ISO,
  "release"?:sha}]}` in the store's order (features by `order`, then by creation).
- `GET /api/admin/ideas` -> `{"ok", "ideas": [record...], "mail": {"configured", "from"}, "bot": {"configured"}}`,
  `GET /api/admin/ideas/<id>` -> `{"ok", "idea"}`.
- `POST /api/admin/ideas/update` `{id, status?, urgency? (null clears), comment?, publicTitle?, publicText?,
  visible?, release?, order?}` -> `{"ok", "idea"}`.
- `POST /api/admin/ideas/note` `{text, contact?, lang?, urgency?, kind?: note|feature, publicTitle?}` -> `{"ok", "idea"}`.
- `POST /api/admin/ideas/reply` `{id, text}` -> `{"ok", "idea", "mail"}` (queued with the undo window).
- `POST /api/admin/ideas/mail/cancel` `{id: mailId}` -> `{"ok"}`, 409 when already sending or sent.
- `POST /api/admin/ideas/done` `{id, summary: {lang: text}}` -> `{"ok", "idea", "draft"}` (draft null without an e-mail).
- `POST /api/admin/ideas/send-done` `{id}` -> `{"ok", "idea", "mail"}`; `POST /api/admin/ideas/mail/send`
  `{id: mailId}` sends a waiting, failed or unknown e-mail again (explicit).

## Tests (stdlib, no network; a fake Telegram API server and a fake SMTP server)

Negative controls: wrong secret -> 403, another chat ignored, Cancel in the undo window sends nothing,
the same e-mail never twice, no done e-mail without Send, the roadmap leaks no contact, migration loses
nothing, an update that is not GSFPV's (a reply to another site's note, a stranger's button) does nothing
and writes nothing, no buttons without the webhook secret, another service's webhook is not taken, the tool
does not crash on a cp1252 console.
