# v0.7 lane D2 — radio: rates types with an editor (+ Quick), channel functions

Two ideas of a Polish pilot from Telegram (docs/wip/v07-plan.md, "Telegram ideas"):

- R-20261006-0001: "choose rates by type: Betaflight, Raceflight, KISS, Actual, Quick, and edit them
  manually in the options".
- R-20261006-0003: "change which radio channel does what, e.g. mode on CH5 and arm on CH6 like on my
  radio; I don't see such an option".

## 1. Rates

### What exists

`packages/sim-core/src/rates.ts` has four curves (Betaflight, Actual, KISS, Raceflight) checked against
compiled Betaflight 4.5.1 (A3, 1880 values, 1e-9). The setting `tune.rates` (per drone, json) is shown
read-only in Settings and filled only by "Import Betaflight diff"; `bfdiff.ts` refuses `rates_type = QUICK`.

### Changes

- **Quick in sim-core** (`rates.ts`): the fifth curve, re-implemented from Betaflight 4.5.1
  `src/main/fc/rc.c` (the Quick rates function and its `quickrates_rc_expo` branch), bounds from
  `controlrate_profile.c` (`255, 200, 100`). `RatesConfig` gains `quickRcExpo?: boolean` (the CLI's
  `quickrates_rc_expo`, OFF by default); `setpointRate` takes it as an optional last argument, so every
  existing caller and the A6 trace stay as they are. A rate of 0 (impossible in the firmware, CLI minimum
  1) gives 0 deg/s instead of the firmware's division by zero.
- **Reference values for Quick**: the function as written in `rc.c` transcribed into a throw-away script
  outside the repository (double precision, the firmware's `uint16_t` products kept), evaluated on
  parameter sets x stick positions; only the numbers are committed
  (`packages/sim-core/test/vectors/rates-bf451-quick.json`), as for A3. Negative controls: the expo
  applied the other way (the `quickrates_rc_expo` branch) and a max rate without the `MAX(..., rcRate)`
  floor are both caught.
- **Editor model** (`packages/sim-core/src/rates-edit.ts`, pure, Node-tested): per type the three
  fields with Betaflight Configurator's names, display scale, step and bounds
  (Betaflight: RC Rate / Super Rate / Expo; Actual: Center Sensitivity / Max Rate / Expo; Quick: RC Rate /
  Max Rate / Expo; KISS: RC Rate / Rate / RC Curve; Raceflight: Rate / Acro+ / Expo); typed values to
  CLI integers with clamping that says so; the max deg/s per axis; curve samples for the chart;
  `ratesCli()` ("copy as CLI": `set rates_type = ...` and the per-axis lines, which `parseBetaflightDiff`
  reads back to the same config); `fitRates()`, the type switch.
- **How a type switch converts** (`fitRates`): the new type's integers (within its bounds) whose curve
  is closest to the old one: least squares of deg/s on 41 stick positions 0..1 (the curves are odd),
  full stick weighted 20x so the max rate matches first. Search: every expo of the new type in steps of 5
  with a pattern search over the other two integers (diagonal moves too), then a 3-D pattern search
  (steps 8..1) from the three best; deterministic. The editor says how far apart the old and new curves are at worst (deg/s).
  Same type in, same config out. Betaflight Configurator resets to defaults on a type change instead;
  the owner's pilot asked to keep his feel, so we convert.
- **prefs** (`defs/tune.ts`): `QUICK` in `RATE_TYPES` / `RATE_BOUNDS` (a test keeps them equal to
  sim-core), `quickRcExpo` kept only for QUICK. No schema version bump. `gen-catalog` outputs change
  (5 rate types).
- **bfdiff**: QUICK accepted, `quickrates_rc_expo` read for QUICK (OFF/ON, anything else refused).
- **Settings editor** (`apps/fly/src/ui/settings/rates-editor.ts`, replaces the read-only view): type
  select; per-axis number inputs with the type's names and bounds; rate limit; a live SVG chart of the
  three curves with the max deg/s per axis; reset to the drone's default (the preset, i.e. `null`);
  Import from Betaflight (as before); Copy as CLI. Strings in a new namespace
  `packages/i18n/locales/fly/rates/`.

Sim determinism: nothing in the default path changes (Pavo20 presets are Actual); A6 must stay
`1d01ca5b...`.

## 2. Channel functions ("Switches")

### What exists

The wizard (`packages/input/src/calib.ts`) finds the arm switch by a flip (`Profile.arm`: an axis
threshold, a button, a momentary button that latches, or the Space key) and on its check screen the
mode switch by a flip with no click (`Profile.modeSwitch`, `mode-switch.ts`: positions are thirds of the
travel). Nothing lets a pilot say "ANGLE on CH6 1300-1700" as in Betaflight's Modes tab.

### Model (`packages/input/src/switches.ts`, no DOM)

- `Profile.switches?: { v: 1, ranges: SwitchRange[] }`, `SwitchRange = { fn, input, lo, hi, and? }`:
  Betaflight's mode activation conditions. `lo`/`hi` in microseconds 900..2100, step 25; a range is on
  when `lo <= value < hi`, the value clamped to 900..2099 (Betaflight `isRangeActive`). Several ranges of
  one function OR together; AND ranges as Betaflight's `updateMasksForMac` (on when any OR range is on,
  or when it has AND ranges and all of them are on).
- Functions: `arm`, `angle`, `horizon` (flight mode: Angle wins over Horizon, neither is Acro, as
  Betaflight `core.c`), and the app's actions that make sense on a switch, by their keymap ids:
  `respawn.rewind`, `respawn.start`, `record.toggle`, `pause.toggle`, `scene.next`, `scene.random`,
  `hud.toggle`. An action runs once each time its switch enters the range (the first frame only learns
  where the switch is, as the arm gate wants it seen off first).
- Channel value: an axis channel is `1500 + 512 * v` (EdgeTX sends +-100 % as 988..2012 us over CRSF,
  the HID report carries the same +-100 % as +-1); EdgeTX's USB joystick reports CH9..CH32 as buttons
  (on when the channel is above its centre), so a button input reads 2012 / 988. The UI names inputs as
  channels: axis i = CH(i+1), button b = CH(b+9) on a USB radio, "button n" on a gamepad.
- Which decides: arm = the arm ranges when there are any, else the wizard's arm (`Profile.arm`, Space and
  latching buttons included). Flight mode = the angle/horizon ranges once `switches` exists (none: the
  pilot's own mode, M / chip), else the wizard's mode switch as today. Without `switches` nothing changes.
- Default shown on the Switches screen = the wizard's result as ranges (`switchesFromProfile`): the arm
  threshold to a range, the mode switch's positions to bands low 900-1325 / middle 1325-1675 / high
  1675-2100 (the thirds of the travel on the 25 us grid). Saving writes `switches`; "Back to the wizard's
  setup" removes it. A new wizard run makes a new profile (the wizard's result is the default again).
- "Flip the switch to assign": the wizard's `ModeSwitchDetector` (stick channels excluded); the range
  becomes the band the switch was flipped to.
- Betaflight import: `parseBetaflightDiff` returns the `aux` lines (`aux i permanentId channel start
  end logic linked`, permanent ids from `msp_box.c`; unusable ranges `start >= end` skipped; a `map`
  line that moves AUX channels is applied) and `switchesFromBetaflight` keeps ARM, ANGLE, HORIZON and
  lists every other mode as not used by the simulator (AIR MODE, BEEPER, PREARM...).

### App

- `mapFrame` / `Controls` (apps/fly/src/controls.ts): arm and mode from the ranges as above; actions go
  to `KeyRouter.trigger(action)` (new: runs the action's handler as its key would, honouring blocks and
  the crash state) from a feature `app/builtin/switches.ts`. Keyboard and touch never read switches;
  a gamepad or radio without `switches` behaves exactly as before.
- Screen: Controls -> the radio in use -> "Switches" (`apps/fly/src/ui/switches.ts`): rows Arm, Flight
  mode (channel + what each position gives, then the Angle / Horizon ranges), Functions (add / remove);
  each range row has a channel select (CH5..CH16), a live bar 900..2100 us with two range handles and
  the channel's marker, and "Flip to assign"; Import from Betaflight (paste `diff all`); Save / Cancel.
  Settings -> Input links to it (the place the pilot looked). The check screen says when Switches
  decide arm and mode. Strings in `packages/i18n/locales/fly/switches/`.

## Tests (each with a negative control)

- Quick vectors (1e-9) + two broken variants caught; the other four types unchanged (A3).
- Editor model: bounds/clamping per type, display scale round trip, invalid input refused, CLI text ->
  `parseBetaflightDiff` -> same config; `fitRates` within a small error where an exact match exists,
  while the unconverted numbers (a naive type switch) miss by hundreds of deg/s.
- bfdiff: QUICK and `quickrates_rc_expo`; aux lines, `map`, a bad aux line refused.
- Switches: range edges as Betaflight, OR/AND against a transcription of the firmware's mask algorithm on
  random configurations (a naive "all ranges AND" is caught), angle over horizon, defaults equal to the
  wizard's arm / mode on a sweep of frames, action edges, import mapping; `Controls` arms and changes
  mode through ranges, actions reach `KeyRouter.trigger`.
- A6 Node hash unchanged.
